### 全局索引上移工具层 + 记账自动化（方案二）

**背景**：超长会话管理原先有个断链——全局索引（L0 注册层）**只能靠人工触发全量重建**。
导入 / 打标 / 检索侧改标签之后，都必须手动补跑一次 ``scan``，否则账本陈旧，
跨库检索会**静默漏掉**刚导入的会话。「盘点」被迫成了必经流程，日常运作上不可用。

**决策**：不做「另写一套增量 append」，而是把归并核心**上移**到工具层，
让「记账」与「盘点」共用同一套代码。

新增 ``autodokit/tools/chat_session_global_index_tools.py``（唯一实现）：

- ``rebuild_global_index(root, library_names=None)``：``None`` 为全量盘点；
  给定库名集合为**作用域模式**——先按 ``library`` 字段撤下这几本库的旧记录，
  再把磁盘当前状态重新归并回去；
- ``record_library_in_global_index(library_dir)``：单库记账便捷入口；
- ``search_global_index`` / ``global_index_status`` / ``global_index_tags_summary`` /
  ``build_global_index_report``。

**为什么「作用域重算」优于「增量 append」**：前两本账（``session_registry`` /
``pair_global_index``）都按 id 归并，所以「重算本库那一份」在语义上**等价于**
「记一笔账」，且天然获得两个性质：

1. **幂等**——同一库重复记账结果不变；
2. **会撤旧**——``tag_global_index`` 是**倒排**结构（``tag → 位置清单``），
   若只加不减，已删除 Pair 的位置会残留，使 ``search`` 返回**不存在的 ``pair_id``**
   （静默的错误结果）。作用域重算天然规避。

**计数漂移的根治 + 账 = 仓库**：`tag_vocabulary` 的条目与计数改为由
**合并后的全量倒排索引**推导（`len(tag_global_index[tag])`），
而不是仅由本次扫描的库统计。这样无论全量还是作用域模式，写回的都是真全局观测值——
单库记账不会把全局计数冲成局部计数。

更深一步（同日第二轮）：「账 = 仓库」——计数改为**精确赋值**而非取历史峰值，
且已不在任何库中出现的标签会**从词表移除**。实测存量词表 **888 → 844**：

| 抽查标签 | 原 count（历史累计） | 现 count（真实） |
| --- | --- | --- |
| `性质/长文回答` | 859 | **282** |
| `内容/游戏设计` | 347 | **189** |
| `性质/排障` | 417 | **145** |

对账结果：词表键集合与倒排索引**完全相等**（0 处历史残留、0 处漏登记、0 处计数偏差），
`count` 总和 4549 = 倒排总位置数 4549。
（附带发现：存量词表**本就没有任何 `aliases` 数据**，所以移除 44 个标签未丢失人工归并成果。）

**代价（已在文档中显式声明）**：若某库在盘点时临时读不到，其标签会从词表消失；
库恢复后重新盘点即可复原。若需要「永不缩水的累积账」那是另一种语义，需显式改回。

**原子性收紧**：三本账先各自写入**带进程号**的临时文件（避免并发时互相覆盖），
再统一 ``os.replace``。跨文件的整体原子性仍无法保证，故文档中明确要求串行执行。

**顺带修掉一个静默故障**：``scan_library`` 原先对缺失 ``pair_index.json`` 的**残缺库**
返回 ``ok=True``，于是残缺库会以「0 个问答对」的形态混进账本。现改为显式报入
``broken_libraries``。实测本机 ``动物语言学习…_索引库`` 正是这种残缺库。

**落地范围**（三个技能升级为薄壳，旧版冻结）：

| --- | --- |
| `ao_超长会话全局索引_v2` | 脚本从 1241 行降至薄壳；新增 ``scan --library`` 与 ``record`` |

### 修复千问导出缺陷：助手回答被错标为 ``user``

**缺陷现象**：千问导出的 JSON 消息数组会在真实用户提问**之前**插入一条角色标为
``user``、内容却是**助手既往回答**（略有截断）的消息::

    U1 A1 U2 A2 U3 A3 U4(伪 user，实为 A2 的副本) U5 A4
                                            ↑ 被插入，制造出 U-U 相邻

实测某 43 条消息的导出（23 user + 20 assistant）含 **3 条**伪 user，
与对应助手消息的相似度为 0.976 / 0.982 / 0.981。若不处理，那段助手回答会被当成
用户提问去配对，问答对语义完全错乱。

**为何此前「看起来没出错」**：``build_pairs`` 遇到连续 ``user`` 时用**后者覆盖前者**，
副本恰好被这条覆盖逻辑吞掉了。但代价是**任何真实的连发消息同样会被静默丢弃**——
即旧行为是靠一个副作用侥幸得到正确结果，而非有意为之；一旦顺序反转
（副本位于真实提问**之后**）就会配错。

**修复**（``chat_session_index_tools.py``）：

1. 新增 ``strip_mislabeled_assistant_copies(messages)``，返回
   ``(清洗后消息, 剔除记录)``；剔除记录含原下标、相似度、对应助手消息下标与
   内容开头，供机器与人工核对。
2. ``build_pairs`` 改为**合并**连续 ``user`` 消息（正文空行连接，保留首条轮次号），
   不再丢内容。
3. ``chat_pipeline.py`` 在千问导出路径调用清洗，并**强制汇报**剔除情况
   （剔除是有损操作，静默处理会让人察觉不到导出文件本身有问题）。

**判定依据**（三条同时成立，缺一不可）：

| # | 判据 | 用意 |
| --- | --- | --- |
| 1 | **结构**：该 ``user`` 处于「连续 user」段中 | 副本是被**插入**的，必然破坏 U-A 交替 |
| 2 | **内容**：与之前**全部** ``assistant`` 相似度 ≥ 0.9 | 副本对应几轮之前的回答，不能只比紧邻上一条 |
| 3 | **长度**：不显著长于对应助手正本 | 副本是截断版 |

**第 1 条是防误删的关键**。用户确实可能粘贴助手原话再追问
（「把上面这段改一下：<粘贴>…」），那种消息在内容上与正本极像、长度也接近，
仅靠内容判据会误删；但它**不破坏 U-A 交替**（其后仍跟着助手回复），
结构判据可精确区分。回归测试 ``test_keeps_user_message_that_quotes_assistant_verbatim``
守护这一条。

**开发中踩到的两个坑（均已修正并写进注释）**：

- **长度比方向写反**：初版设「助手长度 / 被检长度 ≤ 1.02」，但副本是**截断版**，
  该比值恒 **≥ 1**（实测 1.045 / 1.036 / 1.038），导致三个真实副本全部漏检。
  正确区间为 ``(0.98, 1.3)``。
- **误以为「内容相等」即可判重**：副本被截断或轻微改写，规范化后并不相等，
  必须用相似度（``difflib.SequenceMatcher``）。另用 ``quick_ratio()``
  （``ratio()`` 的上界，代价极低）做剪枝，避免 O(n²) 全量比对。

**作用范围限千问导出路径**：该缺陷目前仅在千问导出中实测到。判定依赖相似度，
扩大作用面会带来误删用户真实消息的风险，故不做泛化；若后续在其它导出中发现同类
现象，可显式调用同一函数。

**等价性验证**（最强证据）：用修复后的流水线对原文件重跑，``--mode auto`` 命中
已有会话后报 ``skipped / +0 新增 / ~0 修改 / -0 删除``——即产出与既有归档
**逐字节一致**。说明修复在消除隐式依赖的同时未改变正确结果。

回归测试：``tests/test_qwen_export_defect.py``（10 项）。

### 修复：候选链在「API 成功但输出不可用」时不切换

**现象**：同一条命令、同一配置，有时成功有时整批失败：

```
失败 1 / 批 1 ｜ 错误示例: 响应无法解析为标签 JSON：'\n\n{"pair_xxx": ["内容/积木桌游"...
```

重复调用却又能成功——典型的**间歇性失败**。

**根因**：候选链只按 **HTTP 状态**判定成败。模型返回 200 就算成功，
哪怕内容是思考过程或残缺 JSON。于是：

- 本地模型的偶发不可用输出 → 整批失败；
- 「换个模型再试」的能力**形同虚设**（本地不行时不会自动上云端）。

**LLM 调用成功 ≠ 输出可用**——格式错、被截断、答非所问是常态，
只看状态码等于放弃了唯一的兜底手段。

**修复**：

- ``invoke_llm`` / ``_invoke_candidate_models`` 新增 ``response_validator``
  参数：接收模型输出文本，**返回空串表示通过**，非空为失败原因；
- 校验不通过则**计为失败并继续下一个候选**，失败原因写进 attempts；
- 校验器自身抛异常也按失败处理（不得让整条链崩掉）；
- 打标模块挂上 ``_validate_tag_json``：输出必须含可解析的 JSON 对象。
  该校验刻意**无状态**（不查 pair_id 是否齐全）——每次请求的 pair_id 集合
  不同，而它要固定在 ``build_llm_invoke`` 里；残缺键的过滤由
  ``parse_topic_response`` 负责。

**端到端验证**（真实 API，把“会陷入思考的 9B”放在首位）：

```
FAIL qwen/qwen3.5-9b   via lmstudio  输出校验未通过：输出中找不到可解析的 JSON 对象
PASS qwen3.7-flash     via bailian
→ 解析 1/1 对，标签质量正常
```

本地模型的间歇失败不再导致整批失败，而是自动上云端。
回归测试：``tests/test_llm_model_candidates.py`` 新增 5 项（含校验器异常分支）。

### 修复：provider 的 ``extra_body`` 从未生效（且暴露打标整批失败的真因）

**现象**：超长会话打标出现「响应无法解析为标签 JSON：'Thinking Process:…'」
——模型把输出全用在思考过程上，JSON 根本没输出，整批 8 对全部失败。

**排查**：并非模型能力不足。真正原因有两层：

1. **``extra`` 传法错**：``AliyunLLMClient.generate_text(extra=...)`` 是
   ``kwargs.update(extra)`` 直接展开到 ``chat.completions.create()``，
   所以传 ``{"enable_thinking": False}`` 会被当成顶层关键字参数，
   SDK 报 ``unexpected keyword argument``。正确传法是包一层
   ``{"extra_body": {...}}``。
   该缺陷使 provider 的 ``extra_body`` 字段**从未真正生效过**（属死功能）。
2. **百炼路径根本没传**：``_invoke_within_provider`` 的百炼分支委托
   ``invoke_aliyun_llm`` 时未透传 ``extra``。

**修复**：

- 新增 ``build_request_extra(provider, disable_thinking=)`` 统一组装，
  **强制包一层 ``extra_body``**；无字段可传时返回 ``None``；
- 百炼分支透传 ``extra``；其余 provider 同步改用该函数；
- 数据文件新增 ``no_thinking_body`` 字段：百炼 Qwen 用 ``enable_thinking=false``、
  DeepSeek 用 ``thinking.type=disabled``（参数名随厂商而异，不硬编码）；
- ``invoke_llm`` / ``_invoke_within_provider`` / ``tag_pairs_with_llm``
  全链暴露 ``disable_thinking``；
- ``tag_pairs_with_llm`` **默认 ``disable_thinking=True``**——分类/抽取任务
  不需要思考，而思考会吃光输出预算、推高成本、拉长延迟；
- 审计新增 ``switching["disable_thinking"]``，排障时能判断开关是否生效。

**实测效果**（同一真实批次）：

| 设置 | 耗时 | 结果 |
| --- | --- | --- |
| 默认 | 23.4s | 成功但依赖运气（思考与否不确定） |
| ``disable_thinking=True`` | **1.1s** | 成功，标签质量无损失 |

约 **20 倍**提速，且消除了随机失败。

回归测试：``tests/test_llm_thinking_control.py``（9 项），
其中 ``test_extra_must_be_wrapped_in_extra_body`` 守护上述实现陷阱。

而不是假定「本地＝免费所以先用」。

**实测结论**——能否胜任**不取决于参数量，而取决于会不会陷入思考**：

| 本地模型 | 耗时 | 结果 |
| --- | --- | --- |
| ``qwen/qwen3.5-9b``（9B） | 43s | ✗ 输出 6251 字符思考过程，JSON 被截断 |
| ``zai-org/glm-4.7-flash`` | 78s | ✗ 输出 3410 字符思考过程 |
| ``qwen3.8-27b-mlx`` | 70s | ✓ 直接输出合规 JSON |
| ``qwen/qwen3.6-35b-a3b``（MoE） | **55s** | ✓ 直接输出合规 JSON，**最快** |

- 9B 的三种关闭方式（``enable_thinking`` / ``chat_template_kwargs`` /
  ``thinking``）实测均无效；
- 上下文不是瓶颈：本地模型上下文均为 25～26 万（我们只用约 1 万）。

**同时发现**：数据文件未登记这些本地模型，``resolve_model_provider`` 无法
判定归属，会让本地模型名退回 auto 链首位（DeepSeek）而被误路由到云端。
已将实测可用的两个本地模型正式登记进 ``llm_catalog.json``。

**打标默认顺序最终定为**（写入功能侧 ``config/llm_preference.json``）：

| 位 | 模型 | 归属 | 理由 |
| --- | --- | --- | --- |
| 1 | ``qwen/qwen3.6-35b-a3b`` | 本地 | 免费、离线、实测最快 |
| 2 | ``qwen3.8-27b-mlx`` | 本地 | 本地备选（不同模型鲁棒性不同） |
| 3 | ``qwen3.7-flash`` | 百炼 | 本地不可用时上云端，成本等级 1 |
| 4 | ``deepseek-flash`` | DeepSeek 官方 | **唯一非百炼**，抗平台级故障 |

### 模型参数综合判断（实测依据）

| 维度 | 结论 | 依据 |
| --- | --- | --- |
| **上下文** | **32K 足够，不需要长上下文** | 实测单批输入约 10K tokens（8 对对话 ~6.7K + 752 标签词表 ~4K）；即使词表涨到 5000 标签，总输入仍 < 34K |
| **档次** | **中等（成本等级 1～2）** | 任务需中文语义理解 + 严格指令遵循（8 条规则 + JSON + 长词表复用），过小模型（9B 实测）不可用；又不需长链推理，旗舰档（成本 5～7）对本任务属浪费 |
| **关闭思考** | **必须** | 见上「修复」节 |

**词表是 token 大头**：752 个标签约 4478 tokens，占单批输入 38～47%。
这是后续规模增长时唯一需要留意的变量（已实测至 5000 标签仍在 32K 内）。

**成本量级**：全库重打一次（513 对 / 65 批）——
``qwen3.7-flash`` 约 ¥0.6、``deepseek-flash`` 约 $0.32、本地为 0。
**钱不是主要矛盾，稳定性才是**。

### 模型候选清单（「点菜单」）：让业务功能自己排模型优先顺序

**背景**：模型目录（`llm_catalog.json`）已把「有哪些模型、什么能力、什么价格」
变成了数据文件，`find_models` 也能按条件筛。但缺了最后一环——
**调用方选出来的清单传不进去**：`invoke_llm` 只接受单个 `model` 字符串，
且一旦指定就退化为单元素链（锁定即失去兜底）；`provider_order` 只能排
provider，不能排模型。

结果是「超市货架」与「调用入口」之间断链：工具知道货架上有什么，
业务功能却无法说「我要按这个顺序上菜」。

**新增 `model_candidates` 参数**（`llm_providers.invoke_llm`）：

```python
invoke_llm(
    prompt="...",
    model_candidates=["qwen3.7-flash", "deepseek-flash", "qwen3.7-plus"],
)
```

- 按清单顺序逐个尝试，最靠前的优先用；单条失败继续下一条；
- 每条候选自动路由到它归属的平台（`resolve_model_provider`）；
- 命中的位置记在 `candidate_index`，审计的 `switching.mode == "model-candidates"`。

**三种选模型方式的语义边界**（同时给出时的优先级）：

| 方式 | 语义 | 与清单同时给出时 |
| --- | --- | --- |
| （都不传） | 交给 provider 决定 | — |
| `model="x"` | **锁定**，失败即失败 | 以 `model` 为准（锁定语义更强） |
| `model_candidates` | **按序试**清单 | — |

**默认不扩大尝试范围**（`fallback_to_chain=False`）：清单耗尽即失败。
理由：清单是调用方的明确意图，工具擅自换用清单之外的模型会让产出质量
异常时无法归因——分不清是「模型选错了」还是「任务本身有问题」。
确需兜底时显式传 `fallback_to_chain=True`，此时保留
`switching.candidate_failures` 以便回溯。

**新增 `resolve_model_provider()`：为什么不能用 vendor 反查**

两者**不等价**：百炼是聚合平台，`deepseek-v4.1-flash` 的 `vendor` 是 deepseek，
但服务由百炼提供（`provider` 为 bailian）。若按 vendor 路由到 DeepSeek 官方
端点会得到 404。判定顺序：目录 `provider` 字段 → provider 默认/回退模型命中
→ vendor 兜底映射（仅对厂商有专属 provider 者）。

**新增 `model_provider_map()` 预检**：批量反查并标出 `registered=False` 的候选。
拼错模型名是配置里最常见的错误，提前在启动时提示优于等 API 返回 400 再反推。

**返回体形状统一**：链模式也带 `candidate_index`（恒为 `-1`），
调用方无需为本字段做 `None` 分支。

**向下游暴露的顺序维度**：`provider_order`（厂商，粗）与 `model_candidates`
（模型，细）是两个正交维度；同时给出时以 `model_candidates` 为准
（更精确的表达），并提示 ``--provider-order`` 在该情形下不生效。

回归测试：`tests/test_llm_model_candidates.py`（16 项）。

### DeepSeek 独立 provider、provider 级回退与**凭据隔离修复**（同日追加）

**触发**：用户重命名密钥文件（改为 `{名}_api-key_{档案}.txt`）并新增 DeepSeek key，
要求把 auto 路由改成 **DeepSeek → 百炼 → 本地**。

#### 1. 密钥发现兼容新命名（原本已集体失效）

重命名后**三个 key 全部失联**：代码登记的是 `{名}-api-key.txt`，实际文件是
`{名}_api-key_{档案}.txt`。`secrets_manager` 改为：

- 支持 `{名}_api-key_{档案}.txt` / `{名}-api-key.txt` / `{名}.txt` 三种形式；
- **大小写不敏感**（依赖真实目录项名，而非 `Path.exists()` 推断）；
- 新增**配置档案**概念（`profile`）：显式参数 → 环境变量
  `AUTODO_SUITE_SECRET_PROFILE` → `normal` → `autodo-kit` → 其余按名排序；
- 新增 `list_secret_inventory()`（仅列元信息，不读内容）。

#### 2. 凭据隔离修复（安全问题）

测试 DeepSeek 返回 **401**，报错文本里被服务端回显的 key 尾号是 `6f3b`——
而那是**百炼的 key**，DeepSeek 自己文件的尾号是 `7173`。

**根因**：`build_llm_client` 对非本地 provider **只传 `env_api_key_name`、未传 `api_key_file`**，
于是 `load_aliyun_llm_config` 落到 `_iter_default_api_key_file_candidates()`——
该函数**硬编码为 `bailian`/`dashscope`**，结果把百炼凭据发给了 DeepSeek。

**修复**（两层）：

1. `build_llm_client` 始终传入 provider 自己的 `api_key_file` 与 `secret_name`；
2. `_iter_default_api_key_file_candidates(secret_name)` 改为**按厂商限定候选范围**，
   仅 `bailian` 才附带 `dashscope` 与仓库外历史路径。

> **不做跨厂商兼容回退**：逐厂商误送凭据属凭据泄露风险，不能用“兼容”换方便。
> 回归守护：`test_build_llm_client_uses_own_secret_only`。
>
> **方法论教训**：这个 bug 不是靠读代码发现的——`build_llm_client` 的分支逻辑
> 看上去完全合理（“本地才需密钥文件，云端用环境变量”）。是**服务端回显的 key 尾号**
> 与本地文件尾号不一致这一“不相干的细节”暴露了它。
> 启示：跨边界的凭据/标识应主动做**交叉校验**（“发出去的到底是谁的凭据”），
> 而不是假定调用链正确。

#### 3. DeepSeek provider 注册与 auto 优先级调整

依据 DeepSeek 官方文档（`base_url: https://api.deepseek.com`）：

| 项 | 值 |
| --- | --- |
| 默认模型 | `deepseek-flash`（对应 DeepSeek-V4.1-Flash，1M 上下文，支持视觉） |
| 回退模型 | `deepseek-v4-pro`（= 百炼侧的 `deepseek-v4-pro-0813`，不支持视觉） |
| 思考模式 | 默认开启；可经 `extra_body={"thinking":{"type":"disabled"}}` 关闭 |

#### 4. provider 级回退（新增）

### 大模型目录外置为数据文件（LLM Catalog）

**动机**：各家厂商每隔一段时间就会推新模型、下架旧模型，且**不同模型的参数、
能力、价格都不一样**。原先这些全部硬编码在 ``llm_clients.py``（21 个模型的目录、
任务池、回退链、下线映射）与 ``llm_providers.py``（3 个 provider）里，
每次调整都要改代码 + 改测试 + 重新部署。

**新增**：

| 文件 | 作用 |
| --- | --- |
| `llm/catalog/llm_catalog.json` | **单一真相源**：provider 清单与顺序、模型清单（能力/参数/价格/状态）、任务池、回退链、下线映射、厂商规则、地域端点 |
| `llm/llm_catalog.py` | 数据层：加载 + 结构化 + 查询 API（不依赖 `llm_clients`，避免循环导入） |

字段设计参考 VS Code Copilot 的 `chatLanguageModels.json`（`id`/`name`/`url`/
`costLevel`/`maxInputTokens`/`maxOutputTokens`/`toolCalling`/`vision`），
并补充路由所需字段（`family`/`task_types`/`status`/`replacement`/定价明细）。

**按需选模型（本次新增的用户能力）**：

```python
from autodokit.tools import find_models, describe_model

find_models(needs_vision=True, needs_json=True, max_cost_level=2)  # 能力+成本筛选
find_models(min_input_tokens=1_000_000, currency="CNY")             # 上下文+币种
find_models(verified_pricing_only=True)                            # 只要已核对的价格
describe_model("deepseek-flash")["text"]                           # 看全貌
```

筛选维度：任务类型、五项能力位（思考/视觉/工具调用/JSON/流式）、provider、厂商、
生命周期、成本等级区间、最小上下文、币种、价格是否已核对。

**健壮性（关键设计）**：数据文件不可用时**自动退回内置兜底快照**，功能不中断；
失败原因经 `catalog_warnings()` 可查。测试覆盖了文件缺失、JSON 损坏、
重复定义、空目录等路径。

**顺带修正的问题**：

1. **价格币种原先未区分**：`ModelRoutingPlan` 的成本估算文档写「元」，但
   DeepSeek 官方直连按 USD 计费。现每个模型显式声明 `pricing.currency`，
   并注明工具不做汇率换算、跨币种不可相加。
2. **`qwen3.7-max/flash` 的下线标记过头**：上一轮曾把它们映射到 3.8 同档，
   依据仅是「官网主推列表里出现了 3.8」。但官方只列每档主推款，
