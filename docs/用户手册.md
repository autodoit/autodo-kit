# 用户手册

## 命名治理白名单

1. `workspace/config` 键名（含嵌套）默认保持既有契约，不做无差别中英键名重写。
2. `content.db` 中 `uid_` 前缀字段、`cite_key` 字段、`bib_*` 字段属于英文例外白名单。
3. 历史列名 `题录键`、`来源题录键`、`阅读来源题录键` 在初始化/修复时可回迁到 `cite_key`/`source_cite_key`。

autodo-kit 用于提供官方事务、事务工具和最小运行时。未安装 autodo-engine 时，也可以直接执行事务。

本手册只回答“如何使用”和“从哪里进入”，不承担逐项 API 参数说明。逐项契约见 [API手册](API手册.md)，逐项事务清单见 [AOK预置事务手册](AOK预置事务手册.md)。

补充说明：

- AOB 迁移过来的执行能力统一由 `autodokit.tools` 承接。
- `scripts/aob_tools/` 与 `scripts/run_*.py` 只保留参数化薄入口，不再承载核心逻辑。

如果要先判断“这个能力有没有、从哪里调用”，建议按下面顺序查：

1. 全量事务逐项手册：`docs/AOK预置事务手册.md`

4. 扩展与实现约束：`docs/开发者指南.md`

事务可见性口径：

1. 对用户正式可用的事务，至少应同时具备 `autodokit/affairs/<事务名>/affair.py` 与 `autodokit/affairs/<事务名>/affair.json`。
2. [AOK预置事务手册](AOK预置事务手册.md) 由 `scripts/generate_affair_manual.py` 自动生成，默认按含 `affair.json` 的事务目录纳入索引。
3. 仅有 `affair.py`、缺少 `affair.json` 的目录，视为开发中或未完成契约，不作为正式可配置事务对外承诺。

工具可见性口径：

1. 用户公开工具以 `autodokit.tools.__all__`（即 `list_user_tools()` 返回结果）为准。
2. 开发者工具以 `list_developer_tools()` 返回结果为准。

快速自检命令：

```bash
python -c "import autodokit.tools as t; print('user_tools=', len(t.list_user_tools())); print('developer_tools=', len(t.list_developer_tools()))"
python scripts/generate_affair_manual.py
```

常见入口：

1. 事务入口：`autodokit.affairs.LaTeX转Word.affair.execute`，配置 `merge_subfiles=true`。
2. 工具入口（模块级）：`autodokit.tools.latex_subfile_merger.merge_latex_subfiles(...)`。
3. 如果只做合并、不做 Pandoc 转 Word，优先用第 2 种入口。

### 0.1 当前已落地的 A040 / A045 / A050 独立事务能力

围绕这轮“独立事务节点 + 事务请求层”开发，当前用户已经可以这样使用 AOK：

1. A040 的正式入口是 `autodokit.affairs.检索治理.affair.execute(...)`；它已经能够独立执行题录检索治理，并把 metadata 回写到内容主库。
2. A045 的正式入口是 `autodokit.affairs.文献下载与主附件入库.affair.execute(...)`；当前已经完成真实验收，能够承接 A040 候选，下载 PDF，并把主附件事实统一回写到内容主库与附件关系表。
3. A050 的正式入口是 `autodokit.affairs.统一文献预处理解析.affair.execute(...)`；当前已具备独立事务入口和事务请求层适配，但本轮重点完成的是 A030 -> A040 -> A045 真跑闭环，A050 仍建议按单节点调试或主链调度使用。
4. 这三个节点既可以直接通过 `autodokit.run_affair(...)` 调用，也可以先登记为正式事务请求，再由请求总线分发执行。
5. 当前推荐的最短闭环是：A030 生成检索条件 -> A040 补题录 -> A045 下载 PDF -> A050 做统一预处理。
6. CNKI 在线链路当前推荐复用共享 `browser_profile_dir` 与既有 CDP 会话来保留 cookies 和学校登录态；验证码出现时，通过 `allow_manual_intervention=true` 等待人工完成后继续。
7. `cnki_browser_config.vscode_embedded_only=true` 当前只表示“只接管已存在的 VS Code 内嵌浏览器会话”，不是自动启动 VS Code 内嵌浏览器的能力。

TeX 与 Word 相关工具现在拆成 5 个独立入口，适合按需直接调用：

1. `autodokit.tools.latex_subfile_merger.merge_latex_subfiles(...)`：只负责递归展开 `\subfile{...}` 并合并 tex。
2. `autodokit.tools.pandoc_runner.run_pandoc(...)`：只负责统一执行 Pandoc 命令并返回结果。
3. `autodokit.tools.latex_to_word.convert_latex_to_word(...)`：只负责 tex 转 docx。
4. `autodokit.tools.word_to_latex.convert_word_to_latex(...)`：只负责 doc/docx 转 tex。
5. `autodokit.tools.docx_postprocess.add_heading_numbering(...)` 和 `autodokit.tools.docx_postprocess.highlight_tokens_in_docx(...)`：只负责 docx 后处理。

如果你还想保持原来的聚合导入方式，也可以继续用 `autodokit.tools.pandoc_tex_word_converter`，它现在只是兼容入口，不再承载实际实现。

### 3.0 统一后处理执行边界（2026-04）

从本轮版本开始，A010-A160 主链的通用后处理采用“编排层统一触发”模式：

- 不再要求每个事务 `affair.py` 在内部各自执行通用后处理。
- 默认由 PA 编排层在节点结束后统一触发后处理技能。
- 若通过 `autodokit.run_affair(...)` 直调事务，运行时仍提供统一后处理兜底。

建议：

- 主链编排优先使用“PA + 统一后处理技能”口径，保证任务与日志审计一致。
- 单事务本地调试可继续直调 `execute`，但若需要完整审计产物，应补跑统一后处理。

推荐方式：直接导入具体事务脚本并调用 `execute`。

```python
from pathlib import Path
from autodokit.affairs.PDF文件转md文件.affair import execute

workspace_root = Path.cwd()
config_path = workspace_root / "demos" / "settings" / "pdf_to_md.json"
outputs = execute(config_path=config_path, workspace_root=workspace_root)
print(outputs)
```

补充：也可通过桥接入口调用（兼容方式）：

```python
from pathlib import Path
import autodokit as aok

outputs = aok.run_affair(
    "PDF文件转md文件",
    config={
        "pdf_dir": "data/input",
        "output_dir": "data/output",
    },
    workspace_root=Path.cwd(),
)
print(outputs)
```

说明：

- 直接导入事务脚本时，调用链最短，便于针对单事务做调试与问题定位。
- run_affair 默认由 autodo-kit 内置运行时执行。
- 若环境中安装了 autodo-engine，可继续与其调度层配合使用。
- 在进入运行时前所有路径都必须是绝对路径。
- 对 A010-A160 这类主链固定节点，建议同时维护一份显式入口注册表，避免仅靠临时扫描再推断 runner。

### 3.0.1 A060-A160 对齐口径

从 A060 开始，宿主侧通常会同时出现“节点编号名”“官方 affair 名”和“编号补位智能体名”三套称呼。使用 autodo-kit 时建议按以下顺序理解：

1. 先确认宿主是否通过显式注册表把节点映射到了某个官方 affair。
2. 再以对应的 `autodokit.affairs.<事务名>.affair.execute` 作为默认执行入口。
3. 只有在单节点补位、人工指定和排障时，才把宿主编号事务智能体当作解释层读取。

当前最容易混淆的三处是：

1. 当前主链 A060 官方入口已是 `候选文献视图构建`，official affair_uid 已迁为 `ar_A060_综述文献候选视图构建`，只负责综述候选视图构建。
2. 当前主链 A070 同样映射到 `候选文献视图构建` 模块，但 official affair_uid 是 `ar_A070_综述文献研读`，执行模式为 `review_reading`。
3. 当前主链 A075 官方入口仍映射到 `非综述候选种子生成` 模块，但 official affair_uid 已迁为 `ar_A075_普通文献候选视图构建`。
4. A080 当前职责是“普通文献泛读”，official affair_uid 已迁为 `ar_A080_普通文献泛读`，负责把条目推进到 A095。
5. A095 当前职责是“普通文献研读候选视图构建”，official affair_uid 是 `ar_A095_普通文献研读候选视图构建`，模块名与节点职责已保持一致。
6. A100 与 A140 的宿主节点名、official affair_uid 与官方模块名之间仍存在一层“节点职责名 / 实现事务名”差异。

完整节点矩阵与柔性简并建议见 [A060-A160事务对齐说明](A060-A160事务对齐说明.md)。

### 3.1 在线检索文献模块的唯一入口

在线检索文献模块现在统一收敛到 `autodokit/tools/online_retrieval_literatures/` 目录，用户只允许通过 `autodokit.tools.run_online_retrieval_router(...)` 或 `autodokit.tools.online_retrieval_literatures.online_retrieval_router.route(...)` 调用。

说明：

- 在线检索相关的程序、配置文件和实现模块都应放在 `autodokit/tools/online_retrieval_literatures/` 下维护。
- `online_retrieval_router.py` 是唯一对外入口；不要直接调用其中的子模块执行下载、抽取或检索。
- 默认规则配置文件是 `autodokit/tools/online_retrieval_literatures/config.json`。
- 若需要调整跳过规则，应优先改该配置文件，而不是在单个子模块里临时分支。

实现分层（2026-04 起）：

- 请求画像层：`profiles/request_profile.py`
- 路由层：`router/route_entry.py`、`online_retrieval_router.py`
- 编排层：`orchestrators/*.py`、`policies/*.py`、`catalogs/*.py`
- 执行层：`executors/*.py`、`zh_cnki_*`、`en_open_access_*`

用户可见的稳定入口只有两类：

1. `run_online_retrieval_router(...)`：推荐入口。
2. `run_online_retrieval_from_bib(...)`：Bib 批处理入口，内部仍转到 router。

用户不应直接依赖内部文件，例如：

1. `online_retrieval_resolver.py`
2. `online_retrieval_service.py`
3. `school_foreign_database_portal.py`
4. `en_chaoxing_portal_retry.py`

这些文件是开发和排障时使用的内部实现，不是用户级 API。

专题文档：

- 在线检索文献模块专题：`docs/在线检索文献模块专题.md`

### 3.2 Bib 批处理在线检索

如果你手里已经有一个 Bib 文件，并且希望按每条记录批量执行中文下载原文 PDF、英文下载原文 PDF、中文 HTML 结构数据、英文 HTML 结构数据，推荐直接调用通用工具 `run_online_retrieval_from_bib(...)`。

这个工具不放在 `online_retrieval_literatures/` 里，因为它本质上是通用的 Bib 批处理与记录匹配工具，未来也可以被文献导入、题录清洗、候选池构建等功能复用。它只是把 Bib 任务翻译成在线检索路由 payload，然后继续走在线检索三层结构。

示例：

```python
from autodokit.tools import run_online_retrieval_from_bib

result = run_online_retrieval_from_bib(
    {
        "bib_path": r"sandbox/20260407/测试用.bib",
        "output_dir": r"sandbox/20260407/router_bib_tasks",
        "max_pages": 1,
        "en_per_page": 20,
        "max_entries": 0,
        "use_llm_matching": True,
        "llm_api_key_file": r"demos/settings/配置文件/bailian_api_key.txt",
    }
)

print(result["artifacts"])
```

如果你只想保留最薄的命令行入口，也可以继续使用 `sandbox/20260407/run_bib_online_retrieval_tasks.py`，它只是把命令行参数转交给这个工具。

### 3.3 A040 特殊渠道英文下载

A040 的特殊渠道不再是独立脚本模块，而是 A040 事务 `autodokit.affairs.检索治理.affair.execute(...)` 的参数分支。

如果你要让 A040 走特殊渠道，建议在配置里提供以下信息：

1. `enable_special_channel: true`
2. `special_channel_mode: en_special_download` 或 `en_open_access_special`
3. `special_channel.cite_keys` 或 `special_channel.cite_keys_file`

运行后会发生这些事：

1. 先走开放源下载。
2. 下载失败时，再走学校门户重试。
3. 仍失败的条目进入人工清单。
4. 成功文件会被命名为 `att-<cite_key>-<uid_附件>.pdf`。
5. 文件落盘后，会同步回写 `content.db`，更新 `attachments` 与 `literature_attachment_links`。

注意：A040 事务智能体应直接调用 A040 affair 程序，而不是再去找一个独立的特殊下载脚本。

### 3.3 Windows 上用 3060 跑 MonkeyOCR 单篇 PDF

本仓库已经把 Windows 原生解析能力封装成 AOK tool，可直接调用，不需要手工拼 `parse.py` 命令。

成功解析时采用的配置如下：

- 系统：Windows 11
- GPU：NVIDIA GeForce RTX 3060
- PyTorch：2.11.0+cu126
- 设备模式：`cuda`
- 模型：`MonkeyOCR-pro-1.2B`
- 模型权重目录：`sandbox/test monkey ocr/model_weight`
- 运行后端：`transformers`
- 批大小：`2`
- 运行时依赖：`triton-windows<3.4`
- 运行环境变量：`MONKEYOCR_DEVICE=cuda`、`CUDA_VISIBLE_DEVICES=0`、`PYTHONUTF8=1`

推荐的直接调用方式：

```python
from pathlib import Path
from autodokit.tools import run_monkeyocr_windows_single_pdf

result = run_monkeyocr_windows_single_pdf(
    input_pdf=Path(r"D:\workspace\sandbox\test monkey ocr\input\“双支柱”调控与银行系统性风险——基于SRISK指标的实证分析.pdf"),
    output_dir=Path(r"D:\workspace\sandbox\test monkey ocr\output"),
    monkeyocr_root=Path(r"D:\workspace\sandbox\MonkeyOCR-main"),
    models_dir=Path(r"D:\workspace\sandbox\test monkey ocr\model_weight"),
    config_path=Path(r"D:\workspace\sandbox\test monkey ocr\model_configs.local.yaml"),
    log_path=Path(r"D:\workspace\sandbox\test monkey ocr\parse_direct_run.log"),
    device="cuda",
    gpu_visible_devices="0",
    ensure_runtime=False,
)
```

如果你在另一台 Win11 设备或另一个 workspace 里复现，优先检查这几项：

1. 安装 CUDA 版 PyTorch，保证 `torch.cuda.is_available()` 返回 `True`。
2. 安装 `huggingface_hub`、`triton-windows<3.4`，然后下载 MonkeyOCR 模型权重。
3. 将 `model_configs.local.yaml` 的 `device` 改成 `cuda`，并把 `models_dir` 指向你的权重目录。
4. 如果你要手工跑官方仓库，建议继续保留本仓库的 FlashAttention 回退逻辑；否则在 Python 3.13 的 Windows 环境下，官方路径可能因为缺少 `flash_attn` 轮子而失败。

解析完成后，目标输出目录里通常会看到这些文件：

- `*.md`：最终解析结果，适合直接阅读或后续二次处理。
- `*_content_list.json`：页面/元素级内容清单，适合程序消费。
- `*_middle.json`：中间结构化结果，便于排错与再加工。
- `*_model.pdf`：模型阶段可视化图，便于核对版面识别。
- `*_layout.pdf`：布局阶段可视化图，便于检查分区与区域识别。
- `*_spans.pdf`：文本 span 可视化图，便于检查文本块切分。
- `images/`：页面渲染图，供复核与后续人工校验。
- `model_configs.local.yaml`：本次运行使用的本地配置快照。
- `parse_direct_run.log`：实时运行日志，能看到 batch 进度和报错。

如果你只想复现同一套运行环境，直接复用这份目录结构即可：

- `sandbox/MonkeyOCR-main/`：MonkeyOCR 仓库本体。
- `sandbox/test monkey ocr/input/`：待解析 PDF。
- `sandbox/test monkey ocr/model_weight/`：权重目录。
- `sandbox/test monkey ocr/output/`：解析结果目录。

新增可选输入（保持向后兼容）：

- `seed_items`：支持按条目传 `cite_key`、`pdf_path`、`title`、`detail_url`
- `cite_keys`：支持一组 cite_key 批量输入
- `pdf_paths`：支持一组 PDF 绝对路径批量输入
- `content_db`：可选，提供后可辅助补齐标题等检索线索

示例：按 cite_key 列表批量触发中文 HTML 抽取

```python

result = run_online_retrieval_router(
    {

        "mode": "batch",
        "action": "html_extract",
        "cite_keys": [
            "wang-2021-funding-and-team-science",
            "liu-2019-citation-network-dynamics",
        ],
        "workspace_root": "/home/ethan/CoreFiles/ProjectsFile/AcademicResearch-auto-workflow/workspace",

print(result.get("status"))
```

## 5.3 AOK 全局日志配置

如果你使用工作区配置文件运行 AOK 主链，日志开关写在 `workspace/config/config.json` 的顶层 `logging` 字段中。

最小可用示例：

```json
{
    "logging": {
        "enabled": true,
        "snapshot_mode": "log_only"
    },
    "paths": {
        "log_db_path": "/path/to/your-project/workspace/database/logs/log.db",
        "logs_dir": "/path/to/your-project/workspace/logs"
    }
}
```

字段说明：

- `logging.enabled`：是否允许 AOK 写运行日志。`true` 表示写入，`false` 表示关闭。
- `logging.snapshot_mode`：日志快照模式。当前模板默认使用 `log_only`，普通用户保持默认即可。
    可选值：

    - `"log_only"`：仅记录结构化 SQLite 日志，不保存运行时快照（默认）。
    - `"log_and_snapshot"`：在记录 SQLite 日志的同时，保存运行时快照到 `runtime_dir`（用于故障复现与审计）。
- `paths.log_db_path`：AOK 结构化日志数据库路径，通常指向 `workspace/database/logs/log.db`。
- `paths.logs_dir`：运行日志与审计文件目录，通常指向 `workspace/logs`。

常见配置方式：

1. 开启日志：

```json
"logging": {
    "enabled": true,
    "snapshot_mode": "log_only"
}
```

2. 关闭日志：

```json
"logging": {
    "enabled": false,
    "snapshot_mode": "log_only"
}
```

使用建议：

- 只想控制开关时，优先改 `logging.enabled`。
- 想改日志写到哪里时，再改 `paths.log_db_path` 和 `paths.logs_dir`。
- 新项目如果直接使用初始化模板，默认配置文件里已经带有 `logging` 字段，可以直接把 `enabled` 从 `false` 改成 `true`。

注意：

- 不要把 `paths.log_db_path` 误当成开关；它只决定日志数据库写到哪里。
- 如果你的某些工具链依赖全局配置读取日志开关，显式写出 `logging.enabled` 会比省略该字段更稳妥。

## 5.4 工作区迁移后的路径重写

如果你把整个 workspace 迁移到新设备或新目录，但旧的绝对路径仍然写在配置、步骤产物或 SQLite 里，建议先执行路径 inventory，再执行改写。

推荐使用的 skill：`.opencode/skills/workspace-path-migration/`

推荐流程：

1. 先运行 `inventory-only`，查看所有命中的旧路径清单。
2. 再确认 `old=>new` 映射是否完整，尤其是 `workspace_root` 和仓库根路径。
3. 最后使用 `--apply` 真正写入。

调用示例：

```bash
python3 .opencode/skills/workspace-path-migration/scripts/run_workspace_path_migration.py \
    --workspace-root /home/ethan/CoreFiles/ProjectsFile/AcademicResearch-auto-workflow/workspace \
    --mapping "/home/ethan/CoreFiles/ProjectsFile/AcademicResearch-auto-workflow/workspace=>/mnt/research/workspace" \
    --mapping "/home/ethan/CoreFiles/ProjectsFile/AcademicResearch-auto-workflow=>/mnt/research" \
    --inventory-only \
    --report-path /home/ethan/CoreFiles/ProjectsFile/AcademicResearch-auto-workflow/workspace/logs/path_migration_inventory.json
```

说明：

- 默认会排除 `.copilot`，并自动跳过 `<drive>:/Windows`、`<drive>:/Program Files` 与外部盘路径前缀，减少误改风险。
- `inventory-only` 只做扫描，不会写回文件或 SQLite。
- `--apply` 需要在确认清单后再使用。

你可以先把命中的路径理解为三类，再决定怎么处理：

| 分类 | 处理建议 | 典型内容 |
| --- | --- | --- |
| 可迁移 | 默认改写 | `config.json` 的 `workspace_root`、`paths.*`；各 `affairs_config/*.json` 的 `output_dir`、`bibtex_path`、`pdf_dir`、`sqlite_db_path`；SQLite 里的 `pdf_path`、`origin_path`、`structured_abs_path`、`storage_path`、`source_path`、`note_path`、`artifact_path`、`gate_review_path`、`manifest_path`、`chunks_abs_path`、`shard_abs_path` |
| 只读引用 | 可选改写 | `steps/`、`runtime/`、`knowledge/`、`references/structured_*` 下的 JSON/CSV/Markdown 产物里记录的 `note_path`、`pdf_path`、`structured_path`、`normalized_structured_path`、`output_dir`、`config_path`、`workspace_root` |
| 外部资源 | 默认跳过 | `origin_attachments_root`、`template_root`、`venv_path`、用户级 `.copilot`、系统盘前缀、工作区外的数据目录 |

边界上最重要的一点是：`content.db` 不是唯一的路径来源。`steps/`、`runtime/`、`knowledge/` 和 `references/` 里生成的中间结果也经常把绝对路径写回去，所以 inventory 时要一起看。

### 本地 Git 快照与极简任务账本（用户向简要）

概述：AOK 新增了“本地 Git 快照 + 极简任务账本”能力，便于在事务闸门通过时生成可追溯的代码/产物快照并登记回滚计划。该能力为本地-only，不会自动 push 到任何远端仓库。

快速上手（最小示例）：

```python
from pathlib import Path
from autodokit.tools.atomic.task_aok.git_snapshot_ledger import ledger_init, git_create_snapshot_for_task, git_rollback_by_task_uid

root = Path.cwd()
ledger_init(root)
res = git_create_snapshot_for_task(
    root,
    task_uid="task-20260403-001",
    workflow_uid="wf-xyz",
    node_code="nodeA",
    gate_code="pass_next",
)
print('快照已写入：', res['summary_path'])

# 预览回滚
preview = git_rollback_by_task_uid(root, source_task_uid="task-20260403-002", target_task_uid="task-20260403-001", mode="preview")
print(preview)
```

产物位置说明：

- 账本（SQLite）：`workspace_root/database/tasks/tasks.db`
- 快照摘要（JSON）：`workspace_root/logs/git_snapshots/{uid_任务}.json`
- 本地 tag：`aok/task/{uid_任务}`（仅本地）

提醒：

- `git_rollback_by_task_uid` 默认仅做“预览/登记”，不会自动回滚工作区；若需执行回滚，请按审计与人工确认流程执行 `git checkout` / `git reset` 等命令。
- 快照默认包含工作区当前文件状态；`.gitignore` 只忽略 `database/logs/log.db`，其余内容包括附件默认纳入 Git。

非编程用户建议：使用 demo 脚本或由开发者在事务 pass_next 钩子中开启自动快照记录，避免手工操作产生误提交。

## 6. AOB 工具与统一事务

当前 AOK 承接了 AOB 的脚本型能力，并把“工具执行”和“事务编排”分成两层：

- 工具层：7 个原子 AOB tool，适合 Python 直调或被事务复用。
- 事务层：1 个统一 AOB 业务事务，通过 `mode` 选择具体动作。

### 6.1 CLI 薄入口

主入口如下：

```bash
python scripts/aob_tools/aoc.py validate --input libs
python scripts/aob_tools/deploy.py --help
python scripts/aob_tools/library.py items sync --dry-run
python scripts/aob_tools/library.py aggregate-user-content --dry-run
```

这些入口默认优先操作同级 `autodo-lib`；也可通过环境变量 `AOB_REPO_ROOT` 显式指定 AOB 仓库根目录。部分 CLI 子命令支持 `--repo-root`，以具体 `--help` 输出为准。
其中 library runtime 由工具层通过受控 `AOB_REPO_ROOT` 上下文接收仓库根目录；用户通常只需要在 `aob_sync_items`、`aob_aggregate_user_content`、`aob_import_external_templates` 等 Python 入口传入 `repo_root`。

### 6.2 七个原子 AOB tool

- `aob_validate_content`
    - 用途：校验 `libs` 或单个 AOL 输入路径。
    - 适用：修改规则、skills、模板或引擎壳子后先做编译校验。
- `aob_sync_items`
    - 用途：同步内容库清单。
    - 适用：变更 `database/items.csv` 口径或需要刷新条目元数据时。
    - 行为：同步前会调用 AOC 归一化模块扫描 `libs/` 中 agents、skills、rules 及规则类目录；`dry_run=true` 时只输出统计，不写入文件。
- `aob_aggregate_user_content`
    - 用途：把当前设备用户级 AI 内容聚合进 `autodo-lib/libs/`。
    - 适用：需要把散落在 `~/.copilot`、常见引擎目录或 VS Code 用户 prompts 下的 agents、skills、prompts、instructions、settings 统一纳入内容库时。
    - 自动发现：默认扫描 `~/.copilot`、`~/.claude`、`~/.codex`、`~/.gemini`、`~/.opencode`、`~/.cursor`、`~/.lingma`、`~/.qoder`、`~/.qwen`，以及 `AppData/Roaming/{Code|Cursor|Lingma}/User/prompts`。
    - 冲突策略：不删除既有内容；同名内容一致则跳过，来源较新则覆盖，目标较新则保留目标。
    - 结果：返回退出码；library CLI 会输出新增、更新、跳过和来源明细。默认 `dry_run=true`，便于先看预演结果。
- `aob_import_external_templates`
    - 用途：导入外部模板并自动联动同步与入库。
    - 适用：把外部模板目录纳入 `libs/templates/`。
- `aob_convert_workspace`
    - 用途：在模板项目中做跨引擎办公区转换，并先产出 canonical AOL dump 与目标能力校验报告。
    - 适用：`opencode/claude/copilot/gemini/codex` 之间的办公区转换场景。
    - 结果：返回字典而不是单纯退出码，便于事务层拿到 `capability_report`、`canonical_dump_path`、`validation_report_path`。
    - 报告结构：`capability_report.layers` 会按 `L1/L2/L3` 展示能力保持、降级与阻断情况。
- `aob_deploy_workflow`
    - 用途：执行工作流安装部署。
    - 适用：把 `autodo-lib` 内容按 workflow 投影到目标项目。
    - 当前支持：`opencode`、`claude`、`copilot`、`gemini`、`codex` 均可走 workflow dry-run/install；会创建对应办公区壳子及项目级规则文件。
- `aob_check_opencode_deploy_regression`
    - 用途：对 OpenCode 部署结果做最小回归检查。
    - 适用：部署完成后的验收与回归门禁。

Python 直调示例：

```python
from autodokit.tools import aob_deploy_workflow

code = aob_deploy_workflow(
        workflow_id="academic",
        engine_ids=["opencode"],
        target_dir="/home/ethan/ProjectS",
        dry_run=True,
)
print(code)
```

### 6.3 统一 AOB 业务事务

事务名：`AOB统一业务事务`

事务通过 `mode` 参数统一调度上述 7 个 tool：

- `validate_content`
- `sync_items`
- `aggregate_user_content`
- `import_external_templates`
- `convert_workspace`
- `deploy_workflow`
- `check_opencode_deploy_regression`

`convert_workspace` 推荐额外配置：

- `canonical_dump_path`：显式指定 canonical AOL dump 输出文件。
- `validation_report_path`：显式指定 capability 校验报告输出文件。
- `allow_downgrade`：默认 `true`；若设为 `false`，遇到目标引擎能力降级将直接失败。
- `target_capability_mode`：默认 `balanced`；设为 `strict` 时，只要请求能力不能完整保持就阻断转换。

当前 capability report 分层口径：

- `L1`：`project_instruction`、`rules`、`skills`、`agents`、`commands`
- `L2`：`hooks`、`mcp`、`settings`、`policies`
- `L3`：`modes`、`plugins`、`tools`、`themes`、`plans`、`engine_overrides`

canonical AOL dump 会把 `hooks`、`mcp_servers`、`settings`、`policies`、`engine_native` 作为根字段输出。目标引擎若不能完整承接某项能力，会在 `capability_report` 中标记为 `downgraded`；若目标完全不支持且无法保留，则标记为 `unsupported` 并触发阻断。

推荐规则：一次事务只执行一个 `mode`，不要把校验、转换、部署和回归塞进一次调用。

事务调用示例：

```python
from pathlib import Path
import autodokit as aok

workspace_root = Path("/path/to/workspace").resolve()
outputs = aok.run_affair(
        "AOB统一业务事务",
        config={
                "mode": "deploy_workflow",
                "workflow": "academic",
                "engine_ids": ["opencode"],
                "target_dir": "/home/ethan/ProjectS",
                "dry_run": True,
        },
        workspace_root=workspace_root,
)
print(outputs)
```

### 6.4 推荐操作顺序

常见顺序如下：

1. `validate_content`：先校验内容。
2. `sync_items`：如条目口径变化则同步清单。
3. `aggregate_user_content`：仅在需要把用户级 prompts、agents、skills 等沉淀回 `libs` 时执行。
    默认先用 `dry_run=true` 查看覆盖结果，再决定是否正式写入。
4. `import_external_templates`：仅在导入外部模板时执行。
5. `convert_workspace`：仅在需要办公区互转时执行。
    转换前会先生成 canonical dump 和 capability report；若目标为 Codex/Gemini 等新引擎，建议先以 `dry_run=true` 查看降级项。
6. `deploy_workflow`：执行实际部署。
    若目标包含 `gemini`、`codex`，建议先跑一次 `dry_run=true`，确认壳子目录、项目级规则文件与 AOL 投影结果符合预期。
7. `check_opencode_deploy_regression`：部署后做回归验收。

## 7. 阿里百炼大模型统一路由（用户向）

从本轮改造开始，AOK 中涉及阿里百炼大模型调用的事务与工具会统一走路由层，不再建议在业务配置里手写固定模型名。

### 7.1 需要关注的配置

普通使用场景建议只关心“策略意图”，不直接绑定具体型号：

- `routing_profile`：路由场景预设（例如：`balanced_default`、`cost_first`、`quality_first`）。
- `quality_tier`：质量档位（建议：`standard`、`high`）。
- `budget_tier`：成本档位（建议：`cheap`、`balanced`、`premium`）。
- `latency_tier`：时延档位（建议：`low`、`medium`、`high`）。
- `region`：推理地域（例如：`cn-beijing`）。

说明：

- 若不填具体 `model`，系统会按事务类型、输入规模和预算档位自动选模型。
- 填写 `model` 时，系统会视为“显式锁模型”，仅在明确需要复现实验时建议使用。

### 7.2 最小可用示例（推荐）

```json
{
    "routing_profile": "balanced_default",
    "quality_tier": "standard",
    "budget_tier": "balanced",
    "latency_tier": "medium",
    "region": "cn-beijing"
}
```

### 7.3 什么时候不该手写 model

以下场景优先不要手写 `model`：

- 常规生产任务：用于避免官方模型更新后仍停留在旧型号。
- 成本敏感任务（系统会根据输入规模与预算自动调度更合适模型）。
- 需要跨事务统一策略的任务链（防止每个事务各写各的导致行为不一致）。

### 7.4 什么时候可以手写 model

只有以下场景建议手写：

- 可复现实验（必须固定快照版本）。
- 灰度验证（对比新旧模型效果）。

此时建议同时记录：

- 为什么要锁模型；
- 预计解锁时间；
- 回滚到自动路由的条件。

### 7.5 从固定 model 迁移到策略路由

推荐按下面顺序迁移：

1. 把事务配置中的 `model` 改为 `"auto"`。
2. 新增或补齐 `model_route` 字段，至少声明：
    - `task_type`
    - `quality_tier`
    - `budget_tier`
    - `latency_tier`
3. 在回归阶段执行路由合规扫描：

```bash
python scripts/check_aliyun_routing_compliance.py
```

执行结果说明：

- `finding_count = 0`：表示未发现新的硬编码模型默认值。
- `finding_count > 0`：请根据输出中的 `file_path + line` 定位并改为 `auto + model_route`。

### 7.6 日常运维建议

- 优先通过 `budget_tier` 控制成本，不要在事务里手写低价模型名。
- 若线上表现波动，先提升 `quality_tier` 或调整 `latency_tier`，再考虑短期锁模型。
- 视觉类或长文本任务仍建议显式提供 `task_type`，便于路由层正确挑选候选模型。

也可以直接调用工具 API：

```python
from autodokit.tools import run_aob_workflow_deploy

code = run_aob_workflow_deploy(
    workflow_id="academic",
    engine_ids=["opencode"],
    target_dir="/home/ethan/ProjectS",
    dry_run=True,
)
print(code)
```

## 附录：AOK CLI 工具（aok_tool）简介

为了便于在 CI / 脚本或轻量化环境中使用，本项目新增一个轻量 CLI 工具 `aok`，位于 `tools/aok_tool/aok.py`。
该工具目前提供两个子命令：

- `write-log`：把任意文本写入工作区的 AOK 日志数据库（默认 `workspace/database/logs/log.db`）。
- `list-queue`：轻量排查命令。新项目应优先查看 `content.db` 的 `文献流程状态` 及 `文献流程状态总视图`。

安装/调用方式：在仓库根目录使用虚拟环境中的 Python 运行脚本。例如：

```bash
# 列出 A060 队列（最多 50 条）
python tools/aok_tool/aok.py --workspace workspace list-queue --stage A060 --limit 50

# 把本地文件内容写入日志
python tools/aok_tool/aok.py --workspace workspace write-log --message-file ./my_message.txt
```

工具设计说明：

- `--workspace`（或 `-w`）用于指定工作区根目录，便于在不同实例/路径下复用。若不指定则使用当前工作目录（`.`）。
- `write-log` 支持直接从 `--message` 指定文本，或从 `--message-file` 读取 UTF-8 文件，或从标准输入读取。写入时会按 UTC 时间戳写入 `aok_logs` 表。表结构：`id, ts, source, content`。
- `list-queue` 会读取 `<workspace>/database/content/content.db`，并以 JSON 输出 `count` 与 `items` 列表，便于被其它脚本或管道消费。

迁移建议：

1. 旧脚本 `workspace/scripts/write_aok_log.py` 与 `workspace/scripts/list_a060_queue.py` 已迁移到 `tools/aok_tool/`，建议引用新路径或统一在 CI 中调用该 CLI。 
2. 在自动化脚本中若需频繁写日志或查询队列，优先使用 `aok` CLI，以保证路径解析与日志表结构一致。

示例集成（shell）：

```bash
# 在 CI 中把会话摘要写入日志
python tools/aok_tool/aok.py --workspace workspace write-log --message-file ./ci/session-summary.txt --source ci:session

# 取出 A060 队列并传给后续处理脚本
python tools/aok_tool/aok.py --workspace workspace list-queue --stage A060 --limit 100 > /tmp/a060.json
python scripts/process_a060_batch.py /tmp/a060.json
```


## 7.1 本地参考文献清单检索与占位补录（示例）

说明：若已有论文参考文献清单文本，并希望在本地 `content.db` 中批量匹配并为未命中条目插入占位引文，可以使用 `local_reference_lookup_and_materialize`。

最小示例：

```python
from pathlib import Path
from autodokit.tools import local_reference_lookup_and_materialize

# 将参考文献清单放到一个字符串里（可直接粘贴整段文本）
reference_text = """
参考文献
...（省略其余条目）
"""

result = local_reference_lookup_and_materialize(
    content_db_path=Path("workspace/database/content/content.db"),
    reference_list_text=reference_text,
    workspace_root=Path("."),
    top_n=5,
    placeholder_source="placeholder_from_local_reference_lookup",
    print_to_stdout=True,
)

print('summary:', result.get('summary'))
print('matched count:', len(result.get('matched_view', [])))
print('placeholders inserted:', len(result.get('placeholder_view', [])))
```

说明：
- 调用后会在 `content.db` 的 `literatures` 表中为未命中条目插入 `is_placeholder=1` 的占位记录（并写入 `online_lookup_status: pending`）。
- `print_to_stdout=True` 会在终端打印 JSON 摘要，便于即时查看匹配结果。
- 若要后续在线补全，可基于 `placeholder_view` 的 `uid_文献` 发起外部检索并更新记录。

说明：

- 公开工具可直接获得 IDE 形参提示与自动补全。
- 公开工具统一由 `autodokit.tools.__init__` 管理并导出。
- 需要更底层辅助能力时，请参考开发者指南中的“开发者工具”。

## 11. PDF 结构化主链

当前版本起，PDF 相关主链推荐改为：

1. `PDF文件转结构化数据文件`
2. `解析与分块`
3. `向量化与索引构建`
4. `单篇粗读` / `单篇精读` / `综述草稿生成`

主契约说明：

- 单篇 PDF 的主缓存为 `*.structured.json`，schema 固定为 `aok.pdf_structured.v3`。
- 文献主库会把结构化状态写入 `database/content/content.db` 的 `structured_*` 字段。
- 分块结果主契约为 `chunk_manifest.json + chunk_shards/*.jsonl + literature_chunk_sets/literature_chunks`。
- `docs.jsonl` 与单一 `chunks.jsonl` 已退出 PDF 主链，不再作为正式输入。

使用建议：

- 批量结构化时优先给 `PDF文件转结构化数据文件` 提供 `content_db`，让事务自动回写 `structured_abs_path`。
- 做分块时优先传 `content_db` 或 `input_structured_dir`。
- 做单篇粗读、单篇精读、综述草稿生成时，优先传 `input_structured_json`、`input_structured_dir` 或 `content_db`。

## 11.1 当前正式 PDF 主链

当前版本唯一正式支持的 PDF 解析主链是 MonkeyOCR。

使用建议：

- 进入 A060、A080、A100 等正式事务时，只允许复用 MonkeyOCR 解析资产与其状态回写结果。
- 历史上的传统结构化试验链、阿里百炼多模态解析链，已经退出用户可调用能力范围。
- `autodokit.tools.llm_clients` 仍然保留为通用 LLM 能力入口，可继续用于翻译、辅助筛选、抽取与判别等非 PDF 任务；同时它也是 AOE 默认 EA 自动审计链调用阿里百炼模型的正式入口。退出正式范围的只是旧 PDF 解析/后处理职责。
- 若仓库中仍保留旧实现，它们只作为归档备份放在 `autodokit/tools/old/`，不得作为新任务入口。

### 11.1.1 正式使用范围

适合场景：

- 需要进入 AOK 正式事务主链。
- 需要把解析状态写回 `content.db`。
- 需要与 A060、A080、A100 共享同一套解析资产与任务审计口径。

正式原则：

- 只使用 MonkeyOCR 运行时。
- 不再提供任何非 MonkeyOCR 解析工具的公开示例。
- 不再提供旧后处理门面的调用说明。
- 不把“旧 PDF 多模态链已归档”误解为“禁用 llm_clients 整体”；非 PDF 的统一 LLM 调用与 AOE 的 EA 自动审计都仍走 `autodokit.tools.llm_clients`。

### 11.1.2 归档说明

以下内容不再提供公开使用说明：

- 旧传统 PDF 结构化试验链
- 旧阿里百炼多模态解析链
- 基于这些旧链路的任何后处理门面或批量管理脚本

历史项目审计可到 `autodokit/tools/old/` 查看归档源码；当前项目执行请仅使用 MonkeyOCR 主链。
