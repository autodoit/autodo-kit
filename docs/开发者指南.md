# 开发者指南

> 版本：v0.5.0-Compliance  
> 状态：正式下发 (Official Issuance)  
> 核心哲学：**事务实现最小化、路径预处理集中化、运行时能力外置化、函数直调优先、SQLite 主库优先。**

## 1. 序言：愿景与核心架构 (The AOK Blueprint)

### 1.1 愿景与定位
`autodo-kit` (以下简称 AOK) 的定位是 **“自动化任务领域的标准弹药库”**。它不负责复杂的流转调度（那是 `autodo-engine` 的职责），也不负责状态持久化（那是 `task-db` 的职责）。AOK 的唯一目标是提供经过严格工程化、具有高鲁棒性的 **原子工具 (Tools)** 和 **标准事务 (Affairs)**。

在 v0.5.0 版本中，我们彻底告别了基于字符串反射的 `invoke_capability` 模式，全面推行 **“函数直接调用”** 模式。这一转变旨在提升 IDE 的开发体验（类型补全、重构支持）以及 AI Agent 的调用准确度（减少幻觉、节省 Token）。

### 1.2 核心架构模型：三层工具链
AOK 的 `autodokit/tools/` 目录按照逻辑复杂度和调用深度分为三层，形成了一个清晰的依赖漏斗：

| 层级 | 目录 | 职责 | 设计原则 |
| :--- | :--- | :--- | :--- |
| **原子层 (Atomic)** | `autodokit/tools/atomic/` | 基础功能实现（PDF、文献、LLM 等） | **职责单一、无侧开销**、0 业务感知 |
| **适配层 (Adapters)** | `autodokit/tools/adapters/` | CLI 包装、Agent Payload 处理、Runner 包装 | **环境透明、协议转换**、路径预处理 |
| **分组导出层 (Grouped)** | `autodokit/tools/__init__.py` | 统一公开/开发 API 清单 | **语义聚合、隔离出口**、1 秒定位 |

### 1.2.1 通用后处理集中治理（强制）

为消除“各事务分散后处理”导致的口径漂移，AOK 当前采用统一后处理治理：

1. 通用后处理默认由 PA 编排层统一触发，不在事务 `execute` 内分散执行。
2. `affair_auto_git_commit` 仅作为历史兼容装饰器保留，不再承载后处理执行职责。
3. `run_affair(...)` 仍保留统一后处理兜底，保障非 PA 场景可运行。
4. 新增事务时，不得再在事务脚本中复制 Git 快照、任务台账、通用日志落账等通用后处理逻辑。
5. 任何后处理能力升级，优先改统一运行时与编排技能，并同步更新用户手册与开发者指南。

### 1.3 阿里百炼大模型路由：五层目标架构

为彻底解决“各事务/各工具各写各的模型选择逻辑”问题，AOK 对阿里百炼调用统一采用五层路由架构。

#### 第一层：模型目录层（Catalog）

职责：维护模型元数据单一事实源。

- 模型能力：文本/视觉/代码/推理等。
- 规格信息：上下文上限、思考模式支持、地域限制。
- 成本信息：阶梯价格、可用折扣分类。
- 生命周期：稳定版/最新版/快照版、下线替代映射。

要求：

- 新模型接入优先更新 Catalog，不在事务脚本硬编码。
- 下线模型通过替代映射自动迁移。

#### 第二层：策略层（Policy）

职责：把业务需求翻译成路由决策。

- 输入：`task_type`、`quality_tier`、`budget_tier`、`latency_tier`、`risk_level`、`region`。
- 输出：`primary_model + fallback_chain` 与原因码。

要求：

- 业务层只声明策略意图，不直接决定具体模型。

#### 第三层：估算层（Estimator）

职责：根据输入规模估算成本区间，辅助策略选择。

- 输入长度估算（字符/Token 档位）。
- 阶梯计费区间估算。
- 成本优先/质量优先/时延优先权重计算。

要求：

- 估算结果必须可被审计输出，用于后续策略调优。

#### 第四层：调用门面层（Router Facade）

职责：对外提供稳定 API，屏蔽内部路由细节。

- 推荐入口：`resolve_model_plan(...)`、`invoke_aliyun_llm(...)`。
- 兼容入口：`load_aliyun_llm_config(...)`（内部仍走路由层）。

补充口径：`invoke_aliyun_llm(...)` 不只服务 AOK affairs/tools；AOE 当前默认的 EA 自动审计 blocked 裁决，也复用这条统一调用门面。

要求：

- affairs/tools 禁止绕过 Facade 直接写模型选择分支。

#### 第五层：观测治理层（Observability + Governance）

职责：保障路由可观测、可审计、可演进。

- 路由决策日志（命中、fallback、失败原因）。
- 成本估算与实际调用统计。
- 模型更新后的影响面追踪。

要求：

- 每次调用至少记录一次可追溯路由摘要。

### 1.4 路由开发约束（强制）

1. 事务脚本中禁止出现 `if budget: model=qwen...` 这类业务内路由分支。
2. 默认情况下不要在 `affair.json` 中写死 `model`，应使用策略字段。
3. 必须支持“显式锁模型”豁免机制（用于实验复现），并输出审计记录。
4. 涉及 LLM 调用能力变更时，必须同步更新：
  - `docs/API手册.md`
  - `docs/用户手册.md`
  - `docs/开发者指南.md`

### 1.5 路由迁移实施清单（P3-P6）

当你把存量事务/工具从固定模型迁移到统一路由时，按以下顺序执行：

1. 把默认 `model` 从具体型号改为 `auto`。
2. 将事务配置迁移为 `model_route` 策略字段，不在业务代码内写模型分支。
3. 对工具侧统一使用：
  - `resolve_model_plan(...)`
  - `invoke_aliyun_llm(...)`
  - 或 `load_aliyun_llm_config(model="auto", route_hints=...)`
4. 增加静态治理扫描并纳入回归：

```bash
python scripts/check_aliyun_routing_compliance.py
```

5. 对关键链路运行最小回归（至少覆盖文本、长文本、视觉三类任务）。

### 1.6 静态治理口径

`scripts/check_aliyun_routing_compliance.py` 当前阻断以下模式：

- 代码内把 `model` 默认值写成 `qwen-*`。
- 代码内把 `or "qwen-*"` 作为兜底模型。
- `affair.json` 里把 `"model"` 默认写成具体型号。

推荐把该脚本作为 CI 或提交前本地检查步骤，避免新事务回退到“各写各的模型选择”。

### 2.0.1 在线检索模块收口约定

在线检索相关实现已统一放入 `autodokit/tools/online_retrieval_literatures/`，并由 `online_retrieval_router.py` 作为唯一调度入口。

开发约束：

1. 不要在该目录外新增在线检索程序或配置文件。
2. 不要在业务侧直接 import 或调用 `zh_cnki_*`、`en_open_access_*` 这类子模块作为公开入口。
3. 所有在线检索场景应通过 router 注入统一规则，再下发到具体执行器。
4. 新增规则优先写入 `autodokit/tools/online_retrieval_literatures/config.json`，再由 router 注入到运行时配置。
5. 若新增单条/批量执行器，必须保证它们仍可被 router 接管，不能新增平行入口。

补充分层边界：

- `online_retrieval_literatures/` 只放与在线检索强耦合、后续难以被其他文献功能复用的专用实现。

### 2.0.2 A040 特殊渠道实现约束

A040 的特殊渠道逻辑现在必须内聚在 `autodokit.affairs.检索治理.affair` 中，作为参数分支执行，不再维护独立的 `a040_special_channel.py` tools 模块。

实现约束：

1. A040 事务程序应根据 `enable_special_channel` 和 `special_channel_mode` 决定常规流程或特殊流程。
2. A040 事务智能体只负责调用 A040 affair，不应直接绕过事务程序调用内部下载实现。
3. 成功下载后，附件命名规则统一为 `att-<cite_key>-<uid_附件>.pdf`。
4. 下载后的数据库更新应复用 `bibliodb_sqlite.replace_reference_tables_only(...)`，并同步 `attachments` + `literature_attachment_links`。
5. 不要在 A040 中再维护与 A020 割裂的手写 SQL 回表代码。
- 像 Bib 解析、批次遍历、通用记录匹配、任务汇总这类能力，应放在 `autodokit/tools/` 的通用工具层，再由通用工具调用在线检索 router。
- 当前的 `run_online_retrieval_from_bib(...)` 就是这种“通用工具 + 在线路由适配”的示例：它不属于在线检索专属实现，但内部仍通过 router 进入在线检索三层结构。
- 如果未来文献导入、题录清洗、候选池构建等模块也需要批处理 Bib，就应复用这个通用工具，而不是在 `online_retrieval_literatures/` 再复制一份。

分层约束（2026-04 起）：

1. 请求画像层（`profiles/request_profile.py`）：负责中文、英文、中英文不限等约束表达，不承载具体业务分支。
2. 路由层（`online_retrieval_router.py`、`router/route_entry.py`）：负责入口治理、规则注入和调度选择。
3. 编排层（`orchestrators/*.py`、`policies/*.py`、`catalogs/*.py`）：负责输入归一化、来源发现、来源选择、重试和批量组织。
4. 执行层（`executors/*.py`、`zh_cnki_*`、`en_open_access_*`）：负责具体检索、下载、HTML/结构化抽取。

新增扩展要求：

- 新增输入形态时，优先扩展编排层的输入归一化组件，不要把兼容逻辑堆到 router。
- 新增执行器时，优先在执行层增加能力，再由编排层接入调度；禁止直接在 router 里引入大段 if/else 业务逻辑。
- 编排层允许根据请求画像与来源注册表结果自动补齐单篇/批量执行所需字段，但不得改变已有 payload 关键字段语义。
- 涉及联网能力的回归在目标网络设备执行；本地离线开发阶段至少完成静态导入检查与字段契约检查。

### 2.0.3 A040 / A045 / A050 独立事务节点当前状态

围绕“独立事务节点 + 事务请求层”这轮开发，AOK 侧当前已经落地的能力与边界如下。

已完成：

1. `autodokit.tools.affair_request_bus` 已成为正式请求总线，当前只支持 `A040`、`A045`、`A050` 三个目标节点。
2. 请求主记录通过 `git_snapshot_ledger` 写入 `tasks.db.事务请求`，详细 payload 外置到 `workspace/tasks/requests/<请求UID>/payload.json`。
3. 请求分发时不会新造配置，而是先从 `affair_entry_registry.json` 解析对应节点的官方 `config_path`，再把 `business_payload` 覆盖进去生成 runtime config。
4. A090、A105 已能把阅读回流 A040 的需求同时登记为正式事务请求，并按配置选择是否立即 dispatch。
5. A045 已补齐真实下载链的关键缺口：承接最近一次 A040 真实结果、抑制 `query_terms -> title` fallback、把 acquisition 结果桥接到 `online_records`、按 content.db 中文物理列回填 metadata、统一回写主附件事实。
6. A040 浏览器会话参数已经收口到共享契约，当前以 `browser_profile_dir`、CDP 地址/端口、`allow_manual_intervention`、`keep_browser_open` 为主。

当前边界：

1. 请求总线本身只负责登记、装载、runtime config 构造和 dispatch，不负责 AOE 主循环级别的持续调度。
2. `cnki_browser_config.vscode_embedded_only` 目前只是附着约束，不是会话启动器；仓库还没有“自动启动 VS Code 内嵌浏览器 + 建立 CDP”这一正式实现。
3. A050 已接入请求总线，但本轮完成真实验收的是 A030 -> A040 -> A045；A050 仍需补独立链路回归与后续衔接验收。

扩展约束：

1. 如果后续要把新的节点纳入事务请求层，先补 `SUPPORTED_TARGET_NODES`、默认请求类型映射与该节点的 `business_payload` 覆盖逻辑，再写文档，不要先在上层脚本里硬编码旁路分发。
2. A045 后续迭代中，不得重新引入“关键词猜标题下载”的回退路径；下载对象必须优先来自明确 `seed_items` 或最近一次 A040 真实候选。
3. 涉及 content.db 的回填逻辑时，必须继续兼容中文物理字段，不要把英文列名假定重新写回事务内部。

专题文档：

### 2.1 原子层 (`atomic/`)：模块化标准
这是最底层的实现。这里的代码只负责 **“把一件具体的事做到极致”**。
- **无侧开销原则**：导入该层模块不应触发重型初始化（如启动浏览器、加载大型模型）。开销必须延迟到具体的执行函数中。
- **路径处理铁律**：原子层函数**严禁包含**任何路径转换逻辑。它们必须接收 **绝对路径** (`pathlib.Path`) 类型的参数。

```python
    Returns:
        Dict[str, Any]: 包含标题、页数等信息的字典。
    """
    if not pdf_path.is_absolute():
        raise ValueError(f"原子工具必须接收绝对路径，当前为: {pdf_path}")
    
    # 业务细节实现...
    return {"title": "Sample", "pages": 12}
```

### 2.4 AOB 工具迁移约定
`scripts/aob_tools` 的历史执行能力已下沉到 `autodokit/tools/atomic/aob_runtime/`，并通过 `autodokit.tools.aob` 暴露统一调用 API。

- runtime 层：承载 AOC / deploy / library / regression 的核心执行逻辑。
- tools 层：承载统一入口函数（`run_aob_*`）。
- scripts 层：仅允许参数组织与调用 `autodokit.tools`，不再承载核心实现。

AOB 与 AOC 约定：

- `workspace-convert` 不再只是 argv 透传；AOK 侧会先走 `autodokit/tools/aob_workspace_pipeline.py`，生成 canonical AOL dump 与 capability report，再复用 AOC runtime 真正编译。
- AOC runtime 的办公区编译分支和 `aoc compile --engine` CLI 均支持 `opencode`、`claude`、`copilot`、`gemini`、`codex` 五类目标引擎。
- AOL 根对象已把 `hooks`、`mcp_servers`、`settings`、`policies`、`engine_native` 作为一等字段；workspace ingest 会从源办公区附加载体与配置文件中抽取这些字段，canonical dump 使用 `asdict(aol)` 输出完整快照。
- 目标引擎 emitter 会把 MCP、hooks、审批/沙箱策略和引擎原生配置投影到目标配置文件；不能完整保持的项目必须通过 `capability_report` 明示 downgrade。
- `codex` emitter 稳定输出 `AGENTS.md`、`.codex/config.json`、`.codex/skills`、`.codex/rules`、`.codex/commands`，并保留 `mcp_servers`、`approval_policy`、`sandbox_mode` 与 `aolCanonical` 摘要。
- `gemini` emitter 输出 `GEMINI.md`、`.gemini/settings.json` 以及 agents/skills/rules/commands/hooks 的基础目录，并在 settings 中保留 `mcpServers`、hooks 文件索引和 AOL canonical 摘要。
- `deploy_tool.py workflow` 支持五引擎列表：从 `engine_shell_templates/<engine>` 安装壳子，调用 AOC 从 `libs/` 编译内容，并补项目级规则文件。
- `library_tool.py aggregate-user-content` 负责把用户级来源目录聚合到 `libs/`，当前按目录名和文件后缀把内容路由到 `agents`、`skills`、`prompts`、`instructions`、`settings` 等目录，再由 `items sync` 做 AOL 归一化与清单同步。
- `aggregate-user-content` 当前默认自动发现 `~/.copilot`、常见引擎目录以及 `AppData/Roaming/{Code|Cursor|Lingma}/User/prompts`；更复杂的 IDE 私有存储暂不做语义反编译，只在已知目录契约上聚合。
- `run_aob_items_sync(...)`、`run_aob_aggregate_user_content(...)` 与 `run_aob_external_templates_import(...)` 对 library runtime 使用受控 `AOB_REPO_ROOT` 环境上下文传递 `repo_root`，不向 library CLI 注入不存在的 `--repo-root` 参数。
- `run_aob_workspace_convert(...)` 不向 `deploy workspace-convert` 子命令传递 `--repo-root`；workspace 转换只消费项目目录与源/目标引擎。
- `capability_report` 按 `L1/L2/L3` 分层输出；当前显式覆盖 `hooks`、`mcp`、`settings`、`policies` 与 `modes/plugins/tools/themes/plans/engine_overrides`。

开发建议：

- 新增引擎时，先扩展 `aoc_tool.py` 的 AOL 编译/反编译能力，再扩展 `aob_workspace_pipeline.py` 的 capability matrix，最后才修改事务模板和手册。
- 若仅修改 `run_aob_workspace_convert(...)` 的 argv 透传而不更新 pipeline 报告层，会重新退化回“只搬文件、不解释降级”的旧行为。
- 新增 L2/L3 能力时，应先把能力放入 AOL 根字段或明确的 `engine_native` 逃生口，再更新目标 emitter 和 capability matrix，避免只依赖目录名启发式判断。

#### 开发约束

1. **参数传递链**：Python API → CLI args → argparse → 主函数。不要跳过这一链，Python API 的参数签名必须与 argparse 定义一致。

2. **repo_root 传递**：library runtime 通过环境变量 `AOB_REPO_ROOT` 接收仓库根目录，不通过 CLI 参数。`_run_aob_library_with_repo()` 负责在调用前后管理该环境变量。

3. **AOC 依赖**：所有用户内容功能依赖 `aoc_tool.py`。必须在 `AOL运行时可用()` 返回 True 后才可执行。该检查在 `执行聚合用户级内容阶段()` 和 `更新用户级内容()` 中强制执行。

4. **沙盒递归**：沙盒模式通过 `simulate_only` + `resolved_*_override` 实现递归调用，将真实目录替换为沙盒镜像目录后重新执行同一函数。不要试图在函数内部写两套逻辑。

5. **SQLite 注册表**：
   - `user_content_sync_registry` 通过 `(logical_key, side_id)` 作为复合主键
   - 仅在 `update-user-content` 中读写（聚合和发布不使用）
   - 首次同步或注册表缺失时，自动回退到文件 mtime

6. **去污染**：`过滤旧同步污染条目()` 必须在 `计算一键更新决策()` 之前执行，防止历史 vendor 后缀条目污染决策。

## 3. 事务 (Affair) 生态全解析

事务是 AOK 的对外交付单元，由 **“三件套”** 组成：`affair.json` (定义)、`affair.py` (实现)、`affair.md` (说明)。

### 3.1 三位一体的耦合逻辑
- **`affair.json` (接口契约)**：定义输入/输出 Schema。严禁定义调度控制字段（如重试、超时），这些由引擎处理。
- **`affair.py` (业务心跳)**：核心是 `execute(config_path: Path)` 函数。它调用 `tools` 层的能力，管理事务内部的业务流程。事务应尽量保持 **无状态 (Stateless)**。
- **`affair.md` (语义补全)**：这是面向 AI Agent 的核心资源。它用自然语言解释了该事务的业务边界、前置条件和最佳实践，是 AI 进行意图匹配的关键参考。

## 4. 路径治理与环境合规 (Path Governance)

在多根/分布式工作区中，路径是最大的隐患。AOK 实行 **“绝对路径铁律”**。

### 4.1 核心获取链路
1. **引擎提供基准**：`autodo-engine` 在启动时通过工作区协议确定 `workspace_root`  
2. **调度预转换**：在事务执行前，调度器预先将配置中所有的相对路径，基于 `workspace_root` 转换为绝对路径。  
3. **事务纯消费**：`affair.py` 与 `atomic/` 模块只消费转换后的绝对路径，不负责计算路径。

### 4.2 为什么禁止在代码内写死路径？
任何硬编码路径（即使是 `../../`）都会导致：
- 云端/容器化部署失败。
- 换一台机器或更改一个父目录就彻底瘫痪。
- `deploy.py` 无法正确投影内容。

## 5. 开发协同与工程规范

### 5.1 废弃代码处理：不留痕体原则
项目推行 **“非向后兼容”** 的开发风格：
- 修改或弃用内容时，**直接删除**，不保留任何过时代码（如 `old_v1.py`）或补丁文件。
- 这种风格旨在保持代码库的绝对纯净，降低维护负担和 AI 理解成本。

### 5.2 开发者 Demos 编写标准
每个新增的工具必须在 `demos/scripts/` 下提供单文件 Demo。
- **独立可运行**：Demo 必须能脱离引擎独立执行。
- **最小断言**：必须包含基本的输入检查和输出验证逻辑。

### 5.3 文档同步流程

推荐采用“脚本生成 + 手工补充 + CI 校验”的三段式：

1. 事务手册自动生成：修改事务后先执行 `python scripts/generate_affair_manual.py`。
2. API/用户手册手工补充：把新增能力补到 `docs/API手册.md` 与 `docs/用户手册.md` 的索引和示例。
3. 提交前一致性检查：确认源码新增能力在手册可检索，避免“代码有、文档无”。

硬性同步点：

1. 更新工具导出清单后，必须同步更新 `docs/API手册.md`。
2. 若扩展了 `autodokit.tools.atomic.task_aok` 的表结构或公开函数，必须同时更新 API 手册中的字段约定与扩展表说明，避免文档继续停留在旧版双表结构。
3. 若切换或新增文献库/知识库主库接口，必须同步更新 `docs/用户手册.md`、`docs/开发者指南.md` 与相关迁移指南，明确 SQLite 为主库、CSV 为导出/迁移格式。

### 5.4 文档工程化（Sphinx + Markdown）

当前仓库已经内置最小 Sphinx 文档工程，目录在 `docs/sphinx/`。

建议定位：

1. `docs/API手册.md`、`docs/用户手册.md`、`docs/开发者指南.md` 继续作为主编辑源。
2. Sphinx 作为统一构建入口，用于生成可发布站点与统一目录。
3. `docs/sphinx/api_reference.md` 通过 include 方式接入 `docs/API手册.md`，避免双写。

最小构建命令：

```bash

python scripts/generate_affair_manual.py
python -m sphinx -b html docs/sphinx docs/sphinx/_build/html
```

### 5.5 自动更新建议（CI 门禁）

当源码发生以下变更时，建议在 CI 中强制触发文档检查并阻断未同步提交：

1. `autodokit/affairs/**`
2. `autodokit/tools/**`
3. `autodokit/api.py`
4. `autodokit/main.py`

建议门禁动作：

1. 自动执行 `python scripts/generate_affair_manual.py`。
2. 若生成结果有 diff，提示开发者提交更新后的 `docs/AOK预置事务手册.md`。
3. 使用文档同步 Skill（`.github/skills/update-sync/SKILL.md`）生成 `docs/API手册.md` 的补丁建议。
4. 在 PR 模板中强制勾选“已同步 API/用户/开发者文档”。

### 5.6 文档及时更新技能

建议把每次功能开发后的文档同步动作，收敛为可独立调用的技能与智能体：

1. 技能：`cd_软件工具开发文档及时更新_v1`
2. 智能体：`cd_软件工具开发文档维护智能体_v1`

使用口径：

1. `autodokit/affairs/**` 有变更时，优先重新生成 [AOK预置事务手册](AOK预置事务手册.md)。
2. `autodokit/tools/**`、`autodokit/api.py`、`autodokit/__init__.py` 有变更时，优先同步 [API手册](API手册.md) 与 [工具索引](TOOLS.md)。
3. 公开使用方式发生变化时，优先同步 [用户手册](用户手册.md)。
4. 架构边界、约束与扩展规则发生变化时，优先同步本文件。

写作要求：

1. API 手册只写调用契约，不再承担分类导航职责。
2. 工具索引只做快速定位，不重复 API 级参数表。
3. 用户手册只写使用方式，不重复开发者约束。
4. 过时内容直接删除，不保留兼容性副本。

### 新增模块：本地 Git 快照与极简任务账本（开发者备注）

文件位置：`autodokit/tools/atomic/task_aok/git_snapshot_ledger.py`

快速说明：本模块实现本地-only 的 Git 快照与极简 SQLite 账本，用于在事务闸门（pass_next）处做可追溯提交记录与回滚计划登记。为便于协作，开发者需要注意下列要点：

- 单元测试：已增加 `tests/test_git_snapshot_ledger.py`，可通过以下命令单独运行：

```bash
uv run pytest tests/test_git_snapshot_ledger.py -q
```

- 测试/运行注意：测试会在工作区初始化本地 Git（`git init`）、`git add` 与 `git commit`，因此请在隔离的临时工作区或 CI runner 中运行，避免把个人未提交变更误 commit。模块内已设置默认 `GIT_AUTHOR_*`/`GIT_COMMITTER_*` 环境变量以降低因缺少全局 git config 导致的失败概率。

- 集成建议：把 `git_create_snapshot_for_task` 在事务的 `pass_next` 回调中以非阻塞方式调用；示例：

```python
from autodokit.tools.atomic.task_aok.git_snapshot_ledger import git_create_snapshot_for_task

def on_pass_next(workspace_root, task):
  try:
    git_create_snapshot_for_task(
      workspace_root,
      uid_任务=task["uid_任务"],
      workflow_uid=task.get("workflow_uid", ""),
      node_code=task.get("node_code", ""),
      gate_code=task.get("gate_code", "pass_next"),
      includes_attachments=True,
    )
  except Exception as e:
    # 记录但不阻断主链
    from autodokit.tools.atomic.log_aok import append_aok_log_event
    append_aok_log_event(project_root=workspace_root, event_type="snapshot.failed", payload={"error": str(e)})
```

- 回滚策略说明：当前 `git_rollback_by_task_uid` 仅做目标快照的查询与回滚记录登记（`preview` / `planned` / `done` 状态）。若需要自动执行恢复，建议实现受控流程：创建临时分支(`git checkout -b restore-{uid_任务} {commit_hash}`)、人工或自动化校验、再决定是否合并或强制 reset。任何自动执行的破坏性回滚都必须伴随人工确认与审计记录。

- 文档同步：修改或扩展这个模块的接口时，请同时更新 `docs/API手册.md` 与 `docs/用户手册.md`。可使用仓库内的 `update-sync` skill 或手动按 `docs/` 的约定补写内容并提交 PR。

## 7. Third-Party 集成架构

### 7.1 设计原则

`third_party/` 目录用于存放外部工具集及其 AOK wrapper，遵循以下约定：

- **工具与 wrapper 分离**：上游源码（如 whisper.cpp）保持独立，AOK 仅编写 thin wrapper 脚本
- **平台自适应**：wrapper 应处理平台差异（macOS vs Windows、Metal vs CUDA），向上暴露统一接口
- **零 AOK 运行时依赖**：third_party wrapper 不依赖 autodokit，仅需 Python 标准库 + 外部二进制
- **Skill 层调度**：由 `.copilot/skills/` 中的统一入口脚本负责后端路由与调度

### 7.2 会议转写 (meeting-transcriber-whispercpp)

#### 目录结构

```
third_party/meeting-transcriber-whispercpp/
├── README.md                          # 独立使用说明
├── bin/
│   ├── transcribe_meeting_apple.py    # Apple Metal wrapper
│   └── download_model_hf_mirror.sh    # 模型下载（hf-mirror 镜像）
├── models/
│   └── ggml-small.bin                 # 默认模型（465 MB）
├── whisper.cpp/                       # 上游源码（cmake 编译）
│   └── build/bin/whisper-cli          # arm64 + Metal 二进制
```

#### 上游：whisper.cpp 集成

- 上游仓库：`ggerganov/whisper.cpp`
- 编译命令：`cmake -B build && cmake --build build --config Release`（自动检测 Metal）
- 模型镜像：`https://hf-mirror.com/ggerganov/whisper.cpp/resolve/main/ggml-{size}.bin`
- 验证：`whisper-cli -m models/ggml-small.bin -f test.wav` 应显示 `MTL0` GPU

#### Wrapper：transcribe_meeting_apple.py

Python 标准库实现，三阶段流水线：

1. **ffmpeg 转码**：任意音频 → 16kHz 单声道 WAV
2. **whisper-cli 转写**：`--output-json --output-txt --output-csv`
3. **Markdown 生成**：解析 JSON 分段 → 带时间戳的 `_会议记录.md`

关键函数：

| 函数 | 职责 |
| --- | --- |
| `resolve_model_path()` | 查找模型文件（`--model small` → `models/ggml-small.bin`） |
| `convert_to_wav()` | ffmpeg 转码 + 格式校验 |
| `run_whisper()` | 调用 whisper-cli，返回 JSON |
| `format_meeting_markdown()` | JSON 分段 → Markdown（兼容 `transcription`/`segments` 两种格式） |

#### 统一入口：scripts/transcribe_meeting.py

跨平台调度器，职责单一：

```python
def main():
    if backend == "auto":
        backend = "apple-whispercpp" if (Darwin + arm64) else "cuda-funasr"
    if backend == "apple-whispercpp":
        run_apple_backend(args)   # → third_party wrapper
    else:
        run_cuda_backend(args)    # → cuda-funasr legacy
```

路径解析（`resolve_tool_root()`）：向上搜索 + `~/CoreFiles/ProjectsFile/autodo-kit/` 标准路径 + HOME 广度搜索，三级回退确保不同运行场景下都能定位到 wrapper。

#### 扩展新后端

1. 在 `third_party/` 下新建工具目录（如 `meeting-transcriber-openai/`）
2. 编写 wrapper 脚本，暴露 `--audio`、`--output-dir`、`--language` 等标准接口
3. 在 `scripts/transcribe_meeting.py` 中新增 `run_xxx_backend()` 函数
4. 更新 `--backend` choices 与 auto 路由逻辑
5. 更新文档：SKILL.md、API手册 §2.14、用户手册 §12、开发者指南 §7.2
